# Running on an HPC system

Hyperion models are independent. The intended cluster layout is therefore one
serial Hyperion solve per Slurm job, with many jobs in flight, rather than MPI
within every model. The commands below first run the small tied two-component
campaign in `configs/tied-two-component-smoke.yaml`. They do not define a
production emulator design.

## Keep code and generated data separate

Clone the repository into protected project or home storage. Put model inputs,
raw outputs and logs on a filesystem intended for large reproducible data:

```bash
git clone https://github.com/galacticusorg/dust-compendium.git
cd dust-compendium

export DUST_RT_WORK=/path/to/large-storage/dust-radiative-transfer
mkdir -p "$DUST_RT_WORK"
```

Do not commit `.hdf5` inputs, `.rtout` outputs or logs. The campaign YAML,
software versions and compact collected tabulation are the durable provenance.

## Create the tested environment

The supplied environment uses the released Hyperion package with NumPy 1.26.
The NumPy pin is required because Hyperion 0.9.11 uses an API removed in NumPy
2 while writing model inputs.

```bash
conda env create --prefix .conda/hyperion -f environments/hyperion.yml
conda activate ./.conda/hyperion
python -m pip install --no-deps -e .
```

Confirm that both parts of Hyperion are available:

```bash
python -c 'import hyperion; print(hyperion.__version__)'
command -v hyperion_cyl
```

If the site's Conda package does not provide `hyperion_cyl`, build Hyperion's
Fortran solver from source as described in [Installation](installation.md).

## Build the D03 R_V=4 dust resource

The scalar optical-property tables alone are insufficient: the radiative
transfer also needs the angular scattering matrices generated by
`hyperion-dust`. Pinning the input repository makes this step reproducible.

```bash
git clone https://github.com/hyperion-rt/hyperion-dust.git hyperion-dust-0.1.0
git -C hyperion-dust-0.1.0 checkout 66b04df0d06bbd2338ad180bb0ed247cc8d1fe29
(
  cd hyperion-dust-0.1.0
  python setup.py build_dust
)
```

The smoke configuration expects:

```text
hyperion-dust-0.1.0/dust_files/d03_4.0_4.0_A.hdf5
```

## Validate and build the smoke campaign

`validate` needs no Hyperion and should report 54 models: two emitting
components over three disk optical depths, three spheroid optical depths and
three tied spheroid sizes.

```bash
dust-compendium validate configs/tied-two-component-smoke.yaml

dust-compendium build configs/tied-two-component-smoke.yaml \
  --output "$DUST_RT_WORK/models-smoke"
```

Building writes portable Hyperion input files. It is usually light enough for a
login node; follow local policy if model generation must instead happen in an
interactive allocation.

## Submit independent serial models through Slurm

First submit only two models. Replace `PARTITION` and the memory/time requests
with values appropriate to the site:

```bash
dust-compendium run configs/tied-two-component-smoke.yaml \
  --models "$DUST_RT_WORK/models-smoke" \
  --output "$DUST_RT_WORK/output-smoke" \
  --scheduler slurm \
  --concurrency 2 \
  --tasks 1 \
  --nodes 1 \
  --partition PARTITION \
  --walltime 00:30:00 \
  --memory-per-cpu 2048 \
  --limit 2
```

Inspect both logs under `output-smoke/logs/`. When they are valid, rerun without
`--limit` and increase `--concurrency` to the number of simultaneous jobs the
site permits. Completed models are skipped automatically.

The present Slurm backend remains attached while it meters submissions and
collects exit states. Run it inside `tmux` or another site-approved persistent
shell so that losing SSH does not interrupt submission. A manifest-driven job
array backend is intentionally deferred until the production sampling design
and sensible number of panels per array task are known.

## Collect the compact result

```bash
dust-compendium collect configs/tied-two-component-smoke.yaml \
  --output "$DUST_RT_WORK/output-smoke" \
  --tabulation "$DUST_RT_WORK/tied-two-component-smoke.hdf5"
```

The collected file includes the complete campaign configuration as metadata,
including fixed disk/spheroid size ratios, grid choices, photon count and seed
policy. Retain the YAML and collected file; raw model files can be regenerated.

## What the smoke campaign establishes

Success means that the environment, D03 grain resource, tied geometry,
Hyperion solver, Slurm execution, paired seed policy and collection path all
work together. It does **not** establish spatial convergence, photon
convergence, a production parameter domain or an efficient emulator training
design. Those are the next experiments.

The first such experiment is documented in the repository under
``studies/tied-two-component-azimuths``. It generates one-, two- and
four-azimuth campaigns with five independent seed families, so the actual
between-seed scatter and Slurm cost can determine whether extra peel-off
directions are worthwhile.
